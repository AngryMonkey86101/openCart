## Короткий итог

сравнением, каждый запрос к спискам проверяет членство пользователя, SQL везде параметризован,

## P0 — до публичного запуска

### 1. Лимит размера тела запроса

**Проблема.** `readBody()` в `server/src/api.ts` вызывает `request.json()` без ограничения. Ни Node
(`node:http`), ни Caddy по умолчанию размер тела не ограничивают. Один запрос на сотни мегабайт
съест память маленького VPS и уронит сервер для всех. Проверка `initData` происходит до чтения тела,
но аккаунт в Telegram завести несложно, а вебхук `/bot/webhook` читает тело до проверки секрета.

**Что сделать.**
- В `Caddyfile` добавить `request_body { max_size 16KB }` (всем запросам API хватит с запасом).
- В сервере дополнительно отклонять запросы с `Content-Length` больше лимита и обрывать чтение потока
  после лимита (на случай chunked-запросов без `Content-Length`).
- В `bot.ts` проверять секрет вебхука до `request.json()` (сейчас так и есть) и тоже ограничить размер.

### 2. Rate limiting

**Проблема.** Ограничений частоты нет нигде. Риски: перебор кодов приглашений через
`POST /api/families/join`, засорение базы через `POST /items`, нагрузка на CPU проверкой HMAC
при потоке поддельных запросов, спам оповещениями через посредника.

**Что сделать.** Стандартный образ Caddy не умеет rate limiting (нужен модуль `caddy-ratelimit` и своя
сборка), поэтому проще сделать в приложении:
- До проверки подписи: лимит по IP. Реальный IP брать из `X-Forwarded-For`, который ставит Caddy
  (доверять заголовку, только если запрос пришёл от контейнера Caddy).
- После проверки: лимит по Telegram `user.id`. Приложение опрашивает сервер каждые 4 секунды
  (элементы + события), то есть около 30 запросов в минуту в норме. Разумно: 120 запросов в минуту
  на пользователя в целом, 10 в минуту на запись, 5 в минуту на `families/join`.
- Хватит простого in-memory token bucket (`Map` с очисткой по таймеру), сервер один.
- На превышение отвечать `429` с `Retry-After`; клиент должен не показывать это как ошибку при опросе.

### 3. Отзыв приглашения и удаление участников

**Проблема.** Код приглашения (`invite_code`) постоянный: его нельзя сменить, у него нет срока
действия и лимита использований. Любой, к кому попала ссылка (пересланное сообщение, скриншот,
бывший член семьи), навсегда получает полный доступ к списку: видит имена и `username` участников,
может добавлять, удалять и очищать товары. Удалить участника или выйти из списка тоже нельзя.

Сам код стойкий к перебору: 10 символов из 56, около 58 бит. Небольшой перекос из-за `b % 56`
некритичен, но лучше выбирать символы без перекоса (отбрасывать байты ≥ 224).

**Что сделать.**
- Владелец (`families.created_by`) может перевыпустить код: старая ссылка перестаёт работать.
- Владелец может удалить участника; любой участник может выйти из списка.
- Опционально: срок действия приглашения (например 7 дней) или одноразовые приглашения.
- Владелец может удалить список целиком (каскад по `ON DELETE CASCADE` уже настроен).
- Разделить права: удалять список, участников и перевыпускать код может только владелец.

### 4. Бэкапы базы

**Проблема.** Вся база — один файл SQLite в Docker-томе `app-data` на одном VPS. В README есть
ручная команда бэкапа, но регулярных копий нет. Потеря диска, ошибочный `docker compose down -v`
или взлом означают потерю всех списков.

**Что сделать.**
- Ежедневный бэкап по cron на хосте через онлайн-бэкап SQLite (`db.backup()` или `VACUUM INTO`),
  не копированием файла: в режиме WAL копия файла может быть несогласованной.
- Хранить копии вне VPS, но **в России** (152-ФЗ): например объектное хранилище S3 у российского
  провайдера (Yandex Object Storage, Selectel, VK Cloud).
- Шифровать копии перед отправкой (`age` или `gpg`), ключ не хранить рядом с бэкапами.
- Хранить, например, 7 ежедневных и 4 еженедельные копии.
- Раз в месяц проверять восстановление на чистой машине. Бэкап, который не восстанавливали,
  считать непроверенным.
- Снапшоты диска у хостинга полезны как дополнительный уровень, но не заменяют это.

### 5. 152-ФЗ «О персональных данных»

> Это не юридическая консультация. Перед запуском стоит сверить пункты с юристом или с актуальными
> разъяснениями Роскомнадзора, требования и штрафы в 2025 году ужесточались.

**Какие персональные данные обрабатываются.** Telegram ID, имя, `username` (таблица `users`),
`chat_id`, членство в семейных списках, тексты товаров с авторством, журнал действий (`events`, 30 дней).
Пока приложение используется только семьёй, действует исключение для личных и семейных нужд.
При публичном запуске вы становитесь **оператором персональных данных** (самозанятость этому
не мешает: оператором может быть и физлицо).

**Что сделать.**
- **Уведомление в Роскомнадзор** об обработке персональных данных (pd.rkn.gov.ru) до начала
  обработки.
- **Трансграничная передача.** Оповещения уходят через Cloudflare Worker (серверы за рубежом), и в них
  есть имя участника, название списка и товара, `chat_id`. Это трансграничная передача, о ней нужно
  отдельное уведомление в РКН. Варианты: подать уведомление; убрать из текста оповещения имя
  и содержимое («В списке „…“ есть изменения»); или отказаться от зарубежного посредника.
  Передачу в сам Telegram тоже стоит описать в политике.
- **Локализация.** База на российском VPS — требование локализации выполнено. Бэкапы тоже держать
  в России (см. п. 4).
- **Политика обработки персональных данных**, опубликованная и доступная из приложения
  (ссылка в интерфейсе и в описании бота): какие данные, зачем, сколько хранятся, кому передаются
  (Telegram, Cloudflare), как удалить, контакт оператора.
- **Согласие.** При первом запуске показывать короткий экран с согласием и ссылкой на политику,
  сохранять факт и дату согласия.
- **Право на удаление.** Нужна кнопка «Удалить мои данные»: удалить пользователя из `users` и
  `members`, обезличить `added_by`/`done_by`/`actor_id` в оставшихся списках, удалить списки,
  где он остался один. Сейчас удалить свои данные нельзя.
- **Сроки хранения.** Описать и выполнять: события уже чистятся через 30 дней. Добавить удаление
  неактивных пользователей и брошенных списков (например, через год без активности).
- **Минимизация.** `username` и `chat_id` нужны только для отображения и оповещений; не собирать
  лишнего (`last_name`, фото и т. п.), как сейчас и сделано.
- **Утечки.** Определить порядок действий при инциденте: о утечке нужно уведомить РКН в течение
  24 часов, о результатах расследования — в течение 72 часов.

### 6. Заголовки безопасности

**Проблема.** Ни сервер, ни Caddy не ставят заголовки безопасности.

**Что сделать** (проще всего в `Caddyfile`, блок `header`):
- `Strict-Transport-Security: max-age=31536000` (HSTS; `includeSubDomains`, только если все поддомены
  на HTTPS).
- `X-Content-Type-Options: nosniff`.
- `Referrer-Policy: no-referrer` (в URL бывает `?join=<код>`, он не должен утекать по Referer).
- `Content-Security-Policy`, примерно:
  `default-src 'self'; script-src 'self' https://telegram.org; style-src 'self' 'unsafe-inline';
  img-src 'self' data:; connect-src 'self'; frame-ancestors https://web.telegram.org https://*.telegram.org;
  base-uri 'none'; form-action 'none'; object-src 'none'`.
  Проверить в Telegram на iOS, Android, Desktop и Web, что всё работает, и при необходимости
  сначала включить как `Content-Security-Policy-Report-Only`.
- **Не ставить** `X-Frame-Options: DENY`: Telegram Web открывает Mini App во фрейме, вместо этого
  `frame-ancestors` в CSP.
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`.
- Убрать заголовок `Server` (`-Server` в Caddy).
- Скрипт `telegram-web-app.js` грузится с `telegram.org` без SRI: Telegram обновляет его по тому же
  адресу, поэтому хэш поставить нельзя. Это принятый риск всех Mini App, просто учитывать его.

### 7. Секреты

**Что есть.** `BOT_TOKEN`, `WEBHOOK_SECRET`, `NOTIFY_RELAY_SECRET` (`RELAY_SECRET` в Worker) лежат
в `.env` на VPS и в секретах Cloudflare. В git они не попадали (история проверена).

**Почему это критично.** Токен бота — главный ключ: с ним можно подписать `initData` от имени
**любого** пользователя и получить доступ ко всем спискам, а также полностью управлять ботом.
`RELAY_SECRET` позволяет слать через бота произвольные сообщения всем, кто разрешил боту писать.

**Что сделать.**
- `.env` на сервере: `chmod 600`, владелец — пользователь деплоя, не общая учётка.
- Секреты длиной не меньше 32 байт (`openssl rand -hex 32`); `WEBHOOK_SECRET` и `RELAY_SECRET` разные.
- Записать план смены: `/revoke` в BotFather → новый токен в `.env` и в Worker → перезапуск.
  Сменить токен сразу, если он мог утечь (скриншоты, чаты, история браузера).
- В README сейчас предлагается открыть в браузере `https://api.telegram.org/bot<BOT_TOKEN>/setWebhook...`:
  токен останется в истории и синхронизации браузера. Лучше выполнять это `curl` на доверенной машине
  или после настройки очистить историю.
- В Worker сравнивать `X-Relay-Secret` и `X-Telegram-Bot-Api-Secret-Token` за постоянное время
  (как `safeEqual` в `auth.ts`); то же для `webhookSecret` в `bot.ts`. Риск низкий, но исправление дешёвое.
- В Worker ограничить, что принимает `/notify`: сейчас он пересылает в `sendMessage` любой объект.
  Лучше принимать только `chat_id`, `text` и кнопку из разрешённого набора, ограничить длину текста.
- Если вебхук бота не используется (VPS не достучаться из Telegram), удалить вебхук (`deleteWebhook`)
  или направить его на Worker, чтобы `/bot/webhook` на VPS не был лишней точкой входа.
- Включить двухфакторную аутентификацию на GitHub, Cloudflare, в панели хостинга и в Telegram-аккаунте,
  которому принадлежит бот.

### 8. Защита VPS

- SSH только по ключам: `PasswordAuthentication no`, `PermitRootLogin no`, отдельный пользователь с sudo.
- Firewall (`ufw` или правила хостинга): открыты только 22 (лучше ограничить своим IP), 80 и 443.
  Учитывать, что Docker публикует порты в обход `ufw`; в compose сейчас публикует только Caddy, так и оставить.
- `fail2ban` для SSH.
- `unattended-upgrades` для автоматических обновлений безопасности ОС, плановая перезагрузка
  после обновлений ядра.
- Не держать на этом VPS других сервисов.

## P1 — в первые недели после запуска

### 9. Логи

**Ротация.** Docker по умолчанию пишет логи в `json-file` без ограничения размера; при постоянной работе
диск со временем заполнится. В `docker-compose.yml` для обоих сервисов:

```yaml
logging:
  driver: json-file
  options: { max-size: "10m", max-file: "5" }
```

**Персональные данные в логах.** Сейчас в лог попадают:
- `notifier.ts`: `Оповещение отправлено пользователю <chat_id>`, `Telegram не принял оповещение для <chat_id>`
  и название списка в `Оповещения для «<название>»`. Telegram ID — персональные данные, название списка
  иногда тоже (например «Семья Ивановых»).
- `console.error(err)` в `api.ts` и `index.ts` пишет полную ошибку; в будущем туда могут попасть данные
  запроса.

Что сделать:
- Логировать агрегаты («оповещения: 3 отправлено, 1 ошибка») или обезличенные ID (короткий хэш
  с солью), без названий списков и товаров.
- Никогда не логировать заголовок `Authorization` (там `initData` с именем пользователя; по нему
  24 часа можно действовать от имени человека).
- Если включать access-лог Caddy, исключить из него `Authorization` и query-строку (`?join=`).
- Срок хранения логов указать в политике обработки ПДн.

### 10. Проверка `initData`

Сейчас (`server/src/auth.ts`) подпись проверяется верно. Что можно ужесточить:
- **Срок жизни.** `initData` принимается 24 часа. Утёкшая строка (из лога, скриншота DevTools)
  даёт доступ на сутки. Можно сократить, например, до 1–6 часов; но `initData` выдаётся при открытии
  Mini App и не обновляется, поэтому клиент при `401` должен предлагать переоткрыть приложение.
  Альтернатива: обменивать `initData` на короткую серверную сессию.
- **Валидация полей.** `JSON.parse(user)` при некорректном JSON бросает исключение, и запрос
  получает `500` вместо `401`. Проверять, что `user.id` — положительное целое, `first_name` — строка
  (с обрезкой длины), иначе `401`.
- **Время из будущего.** Отклонять `auth_date` заметно больше текущего времени.

### 11. Квоты

Сейчас один пользователь может создать неограниченно списков и товаров (каждый товар до 120 символов).
Добавить мягкие лимиты: например, до 20 списков на пользователя, до 500 товаров в списке, до 50 участников
в списке. Это защищает диск и сервер от злоупотреблений и почти не ощущается обычными семьями.

### 12. Обновления

- Включить Dependabot (или Renovate) в GitHub для npm и Docker-образов, плюс Dependabot security alerts.
- Добавить CI (GitHub Actions): `npm ci`, `npm audit --omit=dev`, тесты, `typecheck` на каждый PR.
- Образы: `node:22-bookworm-slim` и `caddy:2.10` обновлять регулярно (пересборка с `--pull`),
  следить за окончанием поддержки Node 22 (апрель 2027).
- Порядок обновления на сервере: бэкап → `git pull` → `docker compose build --pull` → `up -d` →
  проверка `/healthz`.

## P2 — улучшения

### 13. Ужесточение контейнеров

В `docker-compose.yml` для `app`:

```yaml
read_only: true            # писать можно только в том /data
tmpfs: [/tmp]
security_opt: [no-new-privileges:true]
cap_drop: [ALL]
mem_limit: 256m
pids_limit: 100
```

Для `caddy`: `cap_drop: [ALL]`, `cap_add: [NET_BIND_SERVICE]`, `no-new-privileges`.
Закрепить образы по digest (`image@sha256:...`) и обновлять их через Dependabot.

### 14. Проверка `initData` без токена бота

С Bot API 8.0 `initData` содержит поле `signature` (Ed25519), которое можно проверить открытым ключом
Telegram, зная только ID бота (раздел «Validating data for Third-Party Use» в документации Telegram).
Сервер на VPS не может обращаться к Telegram, а `BOT_TOKEN` ему нужен только для HMAC-проверки.
Перейдя на проверку по Ed25519, можно убрать токен с VPS совсем: взлом сервера тогда не даст
управления ботом. Токен останется только в Cloudflare Worker.

### 15. Мониторинг

- Внешний пинг `https://<домен>/healthz` (например UptimeRobot или аналог в России) с оповещением.
- Оповещение о заканчивающемся месте на диске и об ошибках бэкапа.
- Отслеживать всплески `401`/`429` как признак атаки.

## Что уже сделано хорошо

- Подпись `initData` проверяется по HMAC-SHA256 с ключом из токена бота, сравнение за постоянное время,
  есть проверка срока и тесты (`server/test/auth.test.ts`).
- Каждая операция со списком и товаром проверяет членство (`requireMember`, `itemFamily`); при отказе
  отвечает `404`, не раскрывая существование чужого списка.
- Все SQL-запросы параметризованы, конкатенации нет.
- Защита от выхода за каталог при раздаче статики (`serveStatic` проверяет префикс корня).
- Фронтенд не использует `dangerouslySetInnerHTML`, React экранирует ввод — XSS через названия товаров нет.
- Контейнер приложения работает от пользователя `node`, многоэтапная сборка без компилятора в итоговом
